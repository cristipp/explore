SOTA factoring

Each model writes the best factoring program it can in 1 h; the programs are graded afterwards.

Hypotheses, stated before the runs: (1) a competent coder converges on the state of the art whatever the constraints: with libraries it calls the best library, with references but no libraries it implements the best algorithm, and from memory alone it still implements the best algorithm. (2) Above a competency threshold, the model doesn't matter. To test both, Sonnet 5.5 medium and Opus 5.5 max each ran under three conditions (M, R, L below).

Verdict: both supported. (1) All six runs built a self-initialising quadratic sieve, the standard best method at these sizes. Opus with libraries used the rusqsieve crate and reached 41 digits per prime; from memory alone both models reached 40. Caveat: no run used the web, so the references condition (R) ended up the same as memory only. (2) Sonnet medium matches Opus max from memory (40 = 40), and all six land within 37–41. What differs is the solution each model chose and how long it took to write it (19–53 min).

What each model built

Each model had 1 h to write the best factoring program it could, in Rust, with the grading rules stated up front. M = memory only (std + a small big-int crate whitelist), R = web references allowed (none were used), L = anything (any crate + web). Programs differ only in which solution the model chose and how long it took to write; the chart below checks that their runtime performance is indeed similar.

Hardware: the models ran as Claude Code sessions in the cloud, but built, benchmarked and tuned their programs on this machine, a MacBook Air with Apple M4 (10 cores) and 32 GB. Grading ran afterwards on the same machine, idle.

Sonnet M uses no crates by accident: it asked for num-bigint 0.4, only 0.5.1 was pre-fetched, and after the offline build failed it wrote its own big-integer code instead of switching versions. The rules are the rules, so the run counts as is.
