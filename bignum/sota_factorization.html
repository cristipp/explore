SOTA factoring

Each model writes the best factoring program it can in 1 h; the programs are graded afterwards.

Hypotheses, stated before the runs: (1) a competent coder converges on the state of the art whatever the constraints: with libraries it calls the best library, with references but no libraries it implements the best algorithm, and from training data memories alone it still implements the best algorithm. (2) Above a competency threshold, the model doesn't matter. To test both, Sonnet 5.5 medium and Opus 5.5 max each ran under three conditions (O, W, C below). Later, Sonnet 4.6 at low effort, the weakest model on the plan, ran the same three, to probe the threshold.

Verdict: both hold above a competency threshold, and Sonnet 4.6 low is below it. (1) All six runs by Sonnet 5.5 medium and Opus 5.5 max built a self-initialising quadratic sieve, the standard best method at these sizes, and landed within 37–41 digits per prime: from training data memories alone both reached 40, and Opus with libraries used the rusqsieve crate for 41. Sonnet 4.6 low only got there with the library: it also found rusqsieve (after a web search) and reached 40, but on its own it chose ECM with Pollard's rho (W web, no crates: 26) or wrote a plain quadratic sieve (C no web, no crates: 23), and in both it ran out the hour. (2) Above the threshold the model matters only by a thin margin: Opus max is at or above Sonnet 5.5 medium in every condition, by 0 to 3 digits (O anything goes 41 vs 39; W web, no crates 40 vs 37; C no web, no crates 40 = 40). Below it the model matters a lot (23–26 vs 37–41), unless a library closes the gap. The W web, no crates condition changed behaviour without being used: the 5.5 runs stopped after about 20 minutes (Sonnet 19, Opus 21), against 38–52 for their other four, and scored at or below their no-web twins. What differs above the threshold is the solution each model chose and how long it took to write it.

What each model built

Each model had 1 h to write the best factoring program it could, in Rust, with the grading rules stated up front. O = open, anything goes (any crate + web), W = web, no crates (web allowed but never used; std + the big-int whitelist), C = closed, no web, no crates (std + a small big-int crate whitelist). Programs differ only in which solution the model chose and how long it took to write; the chart below checks that their runtime performance is indeed similar.

Hardware: the models ran as Claude Code sessions in the cloud, but built, benchmarked and tuned their programs on this machine, a MacBook Air with Apple M4 (10 cores) and 32 GB. Grading ran afterwards on the same machine, idle.

Sonnet M uses no crates by accident: it asked for num-bigint 0.4, only 0.5.1 was pre-fetched, and after the offline build failed it wrote its own big-integer code instead of switching versions. The rules are the rules, so the run counts as is.

All the code, with each model’s prompt and the versions saved while it worked: code/.

Isolation: the sessions ran in sibling folders on one machine. Sonnet 4.6 low (W web, no crates) looked into Opus 5.5's W web, no crates folder for its build setup (Cargo.toml, Cargo.lock, the offline crate registry) to get past the same offline num-bigint version problem. It did not open Opus's source code, and it built a different algorithm (ECM). Future runs will be isolated.
