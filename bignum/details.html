1. Findings so far

  1. @simonw's result reproduces, on two models. No-thinking addition in words collapses with operand length: Flash scores 1,489/5,070 on @simonw's full grid (@simonw's 27B: 1,195), and our 27B scores 44/169 on the paired cases (@simonw's: 45/169). With thinking, everything is near-perfect (Flash 169/169).
  2. Multiplication is much harder without thinking. Flash no-think scores 596/5,070 (11.8%) on the full mul + words grid, against 1,489/5,070 (29.4%) for add + words; on the 169 paired cases, 19 vs 48. With thinking, 168/169 at high effort; the 27B reaches 165/169 (high) and 148/169 (medium), but needs far more time: 1–8 minutes per case at the largest sizes.
  3. Factoring in the head stops at about 8-digit products. With thinking, both Qwen models factor the 13 easiest numbers (Flash medium: 16), then run into the 16k-token limit or the 1 h budget (19–30 of 91 attempted). Without thinking: 2–3/91, and 118/2,730 (4.3%) on Flash's full grid, all of them small numbers.
  4. Writing a program from training data memories solves add + words and mul + words outright. Given an hour, no internet and no libraries (Python), both Qwen models at high effort write converters that score 169/169 on each task and 169/169 on a hidden set of fresh cases.
  5. Factoring by program reaches 37–41 digits per prime, above a competency threshold. Sonnet 5.5 medium and Opus 5.5 max, given an hour in Rust with the grading rules stated up front, all build a quadratic sieve. Sonnet 4.6 low reaches 40 only with a library; on its own it reaches 23–26 (see 1b).
  6. Qwen can barely write Rust. Asked for the same converter in Rust, Flash ran out of tokens before producing code; the 27B's program had one compile error (a missing mut) and, once fixed, a spacing bug (8/169).
  7. The higher effort level isn't more thinking for Qwen. On oMLX, "high" maps to the template's xhigh, which produces shorter reasoning than "medium".

  • Convergence on the state of the art: supported above a competency threshold. All six runs by Sonnet 5.5 medium and Opus 5.5 max built a quadratic sieve; with no web and no crates they come within 1 digit of the library-based best (40 vs 41). Sonnet 4.6 low, the weakest model on the plan, only got there with the library (40, after finding rusqsieve by web search, the only run to use the web); on its own it chose ECM with rho (26) or wrote a plain quadratic sieve (23), and ran out the hour both times.
  • Above a competency threshold the model doesn't matter: mostly. The model matters only by a thin margin. Opus max is at or above Sonnet 5.5 medium in every condition, by 0 to 3 digits per prime (anything goes 41 vs 39, web, no crates 40 vs 37, no web, no crates 40 = 40). Below the threshold it matters a lot (23–26), unless a library closes the gap (40).
  • "Web, no crates" changed behaviour without being used. Both 5.5 runs in it stopped after about 20 minutes (their other four took 38–52) and scored at or below their no-web, no-crates twins (Sonnet 37 vs 40, Opus 40 = 40).
  • Isolation slip: the sessions ran in sibling folders. Sonnet 4.6 low (web, no crates) read Opus 5.5's build setup (Cargo.toml, Cargo.lock, the crate registry) to get past the offline num-bigint version problem; it did not open Opus's source and built a different algorithm.
  • A self-inflicted handicap (Sonnet M): it wrote num-bigint = "0.4" from training data memories, but the pre-fetched whitelist was 0.5.1. The offline build failed with cargo naming the available version, and Sonnet then dropped all crates and wrote its own big-integer arithmetic instead of switching to 0.5. A dumb error, but within the rules, so the run counts as is; it still reached 40.
  • Above the threshold, the only real difference is the solution chosen and how fast it was written (19–53 min). Runtime per number near the frontier is within about 2× across the six 5.5 runs (sota_factorization, frontier chart).
  • Usage: the six 5.5 runs cost about +1% of the weekly plan limit; the three Sonnet 4.6 low runs about +2% (39% → 41%).

Each wrong but well-formed answer is compared with the correct one group by group. Groups are the 3-digit chunks that map to "… million", "… thousand".

Reading:

  • It's not mainly carry slips. Clean ±10^k errors are 4–6%, and carries into the first wrong group are only modestly enriched (39% vs 30% chance).
  • The leading group is almost always right, then it drifts. The model gets the magnitude and first group right, then produces plausible but wrong groups for the rest (often several groups). That fits emitting most-significant first with no scratchpad: it commits to the first group (which mostly depends on the leading digits) and has to improvise the rest.
  • Two distinctive failure modes cover ~9%: echoing the long operand unchanged, and adding the short operand at the wrong place value. Both are about alignment, not arithmetic.
  • Flash and the 27B fail in almost the same way, so this looks like a property of the task and decoding regime rather than of one checkpoint.

6. Notable failures and anomalies

  • Sonnet medium, SOTA M, crate version: asked for num-bigint 0.4 while only 0.5.1 was pre-fetched (the prompt says the crates are downloaded but not which versions). The offline build failed, and the model wrote its own big-integer code rather than retry with 0.5. Counted as is; the other three whitelist runs used 0.5 or "*" and built fine.
  • Budget overshoot: some in-head arms ran past their 1 h by one slow case (up to 4,124 s for 27B factoring with high thinking), because the HTTP timeout bounded each socket read, not the whole request. Requests now have a hard wall-clock deadline; the affected runs keep their recorded times, and the one extra case each makes almost no difference to their scores.

7. Method

Hardware: see section 4 (@simonw on an NVIDIA DGX Spark; our Qwen runs on an M5 Max MacBook Pro via oMLX; Claude's factoring programs built and graded on an M4 MacBook Air).

In-head arms: one request per case, one at a time, greedy decoding, 16k-token cap, 1 h per arm. add + words uses @simonw's cases, prompt and grader unchanged; mul + words swaps + for ×. SOTA arms: 1 h of development (Qwen: Python, no web, no libraries; Claude: Rust under conditions M / R / L), graded afterwards on fresh cases, factoring on 16 balanced semiprimes per size at 60 s per number.
